UI Design Lab — Menu

Working visual specification and comparative reference laboratory for the Menu component.

Purpose of this Design Lab: establish the visual and interaction direction for application menus through direct comparison with representative productivity and desktop interfaces. Numeric values shown here are provisional until validated against screenshots and application requirements.

1. Menu Role & Current Design Hypothesis

Establish what the Menu is responsible for before comparing individual visual treatments.

The Menu provides a transient collection of related commands, actions or navigation choices. It should support rapid desktop interaction while remaining visually subordinate to the application content that opened it.

Current design hypothesis: Menus should use a quiet surface and restrained border treatment, with a subtle shadow reserved for communicating that the menu is floating above the underlying application surface. Menu-item hover should provide clear but restrained feedback, using the established very-light Claro Blue direction where appropriate.

Important: Unlike the Button component, a Menu is an overlay. Therefore the absence of general elevation in the Design System does not automatically mean that a Menu must have no shadow. The necessity, strength and geometry of the Menu shadow should be resolved here as a component-specific treatment.

8. Menu Design Questions to Resolve

Questions to settle before Menu becomes a finalized component specification.

  1. Should all floating Menus use a border, or can the surface/shadow combination establish sufficient separation?
  2. What shadow treatment is appropriate for a Menu, given that elevation is not a general design-system hierarchy?
  3. What Menu item height should correspond to Compact, Default and Comfortable density?
  4. Should Menu hover use the established very-light Claro Blue surface, or should Menu use a distinct hover treatment?
  5. How should focus-visible differ from hover when navigating a Menu entirely by keyboard?
  6. What is the visual treatment for a persistently selected or checked Menu item?
  7. Should selected and hover states combine, and if so, which visual characteristic remains dominant?
  8. How should disabled Menu items be differentiated from normal items without becoming visually confusing?
  9. Are icons mandatory, optional, or reserved for particular Menu categories?
  10. If icons are optional, should an empty icon column still be reserved to maintain alignment?
  11. How should keyboard shortcuts align?
  12. What is the standard submenu indicator and its reserved width?
  13. What separator spacing provides the appropriate information density?
  14. Are section labels required, and if so, how should they differ from ordinary Menu items?
  15. How should contextual Menus differ from application/command Menus, if at all?
  16. How should a Menu behave when its available viewport space is limited?
  17. What is the appropriate minimum width and maximum width?
  18. Should long Menu labels wrap, truncate, or expand the Menu?
  19. How should destructive commands be visually distinguished?
  20. Which Menu decisions should become global semantic tokens?

9. Submenu & Nested Menu Questions

Nested menus have additional interaction and geometry requirements.

Questions include submenu opening delay, pointer movement between parent and child menus, keyboard navigation, horizontal offset, alignment, shadow treatment and whether nested menus share exactly the same item geometry as their parent.

10. Accessibility & Keyboard Questions

Interaction requirements that should be validated independently of visual styling.

  • Does the Menu receive focus appropriately when opened?
  • Is the currently focused item clearly identifiable?
  • Can users navigate items predictably with Arrow Up / Arrow Down?
  • Is Home / End behavior appropriate for long Menus?
  • Does Escape close the Menu predictably?
  • Do Enter and Space activate the appropriate item?
  • Do arrow keys open and navigate submenus where applicable?
  • Is the keyboard focus treatment distinguishable from pointer hover?
  • Are disabled items skipped or otherwise handled consistently?
  • Are selected/checked states communicated independently of color?
  • Are destructive actions identifiable without relying solely on color?
  • Is the Menu correctly exposed to assistive technology using the appropriate semantic roles?

11. Content & Typography Questions

Menu content can strongly affect perceived density and geometry.

  • Primary Menu label versus shortcut text
  • Label font size and weight
  • Shortcut font size and contrast
  • Icon size and visual weight
  • Long labels
  • Localization and unusually long strings
  • Section labels
  • Destructive command text
  • Submenu indicators
  • Checkmarks and radio indicators
  • Menus containing icons versus text-only Menus
  • Consistency with Button and TextBox typography

13. Current Menu Decisions

Promote established conclusions into the Design System only when they are sufficiently validated.

  • The overall Menu should remain visually restrained and productivity-oriented.
  • Menu hover should be evaluated against the established very-light Claro Blue interaction direction.
  • Menu elevation/shadow should be treated as a Menu-specific floating surface treatment rather than as evidence for a global elevation scale.
  • Focus-visible must remain independently understandable from hover and persistent selection.
  • Menu geometry should be validated against actual reference measurements before becoming a final token set.
  • Reference screenshots are comparative evidence and should not be treated as specifications to copy.
