UI Design Lab — Grid

Working visual specification, comparative-reference gallery and interaction-state laboratory for the Grid component.

Purpose of this Lab: Establish the visual and interaction direction for the application's Grid before final CSS implementation. Reference systems are being studied for principles, geometry and interaction patterns rather than copied wholesale.
Current design hypothesis: The Grid should be information-dense, restrained and highly legible. Borders, row/column structure, selection and interaction states should provide the necessary hierarchy without relying on persistent color, excessive decoration or general elevation.

2. Grid Roles & Anatomy

Identify which visual and behavioral roles the Grid must support.

Element Role Questions to resolve
Grid container Overall visual boundary and scrolling region. Border? Radius? Background? Does the grid visually separate itself from the surrounding application?
Column header Identifies columns and provides sorting/filtering affordances. Height? Background? Border? Typography? Sort indicator? Hover treatment?
Data row Primary information-bearing unit. Height? Gridlines? Alternating rows? Hover? Density?
Selected row Persistent row-level selection. Background? Border? Checkbox? How distinct from hover?
Active cell Cell-level focus or editing target where applicable. Outline? Border? Focus ring? Does active cell differ from selected row?
Row header / number Optional structural/navigation aid. Is it required? How much visual emphasis should it receive?
Toolbar / action area Grid-level commands and controls. Should it visually belong to the Grid or surrounding application chrome?
Pagination / status area Navigation and record-count information. Integrated into Grid boundary or visually separate?

6. Interaction & Accessibility Questions

Visual design should be evaluated together with Grid behavior.

  1. What receives focus when the Grid receives keyboard focus?
  2. Is row selection distinct from cell focus?
  3. Is the focus-visible treatment clearly distinguishable from hover and selected states?
  4. What does Enter do when a row is focused?
  5. What does Enter do when a cell is editable?
  6. What does Space do for row selection?
  7. How do Arrow keys move through rows/cells?
  8. How does Shift + Arrow affect range selection, if supported?
  9. How does Ctrl/Cmd + click affect selection?
  10. How does Escape behave during cell editing?
  11. How are sorting and filtering communicated?
  12. How are disabled/unavailable rows or cells communicated?
  13. Does the Grid support direct cell editing, row editing, or both?
  14. What happens when content exceeds the available cell width?
  15. How should validation/error states appear inside cells?
  16. How should pinned/frozen columns or headers appear?
  17. How should pagination interact visually with the Grid?
  18. Which behaviors are already provided by Dojo and therefore should not be changed merely for visual reasons?

7. Grid Design Questions

Questions to resolve before the Grid becomes a finalized component specification.

  1. How visible should normal Grid borders/gridlines be?
  2. Should every cell have a visible gridline, or should row structure carry most of the visual separation?
  3. Should the header have a distinct surface, border, typography treatment, or combination?
  4. What should the default row height be?
  5. What should Compact and Comfortable Grid density mean?
  6. Should row hover use the same very-light Claro Blue direction as appropriate controls?
  7. Should selected rows use the same surface as hover, or a related but distinct token?
  8. How should Selected + Hover be represented?
  9. What is the visual distinction between selected row and focused/active cell?
  10. Should alternating row backgrounds be used?
  11. How much persistent color is appropriate for selection?
  12. What is the appropriate header typography weight and size?
  13. How should sorting indicators appear without adding noise?
  14. How should column resize affordances appear?
  15. How should editable cells differ from read-only cells?
  16. How should validation/error states appear without relying on color alone?
  17. Should the Grid have a radius, and if so should it use the same radius as other controls?
  18. Which Grid values should become shared global design tokens?

9. Current Working Decisions

Candidate decisions to be retained, changed or promoted as evidence is collected.

D-001 — Information density is a primary Grid concern.

The Grid must support substantially denser information presentation than a consumer-oriented table while retaining sufficient readability and interaction clarity.

D-002 — No general elevation treatment.

The Grid should not receive a generic Material-style shadow merely because it is a component or data surface.

D-003 — Persistent color should remain restrained.

Grid structure should primarily be communicated through typography, spacing, borders and subtle surfaces.

D-004 — Hover and selection must remain distinguishable.

A selected row represents persistent application state; hover represents transient pointer state.

D-005 — Cell focus must remain independently visible.

Where cell-level navigation or editing exists, the active cell must not be confused with ordinary row selection.

D-006 — Semantic tokens first; numeric values provisional.

Grid-specific geometry and colors should eventually consume shared semantic design tokens where the component behavior and visual role justify doing so.

10. Notes for the Reference-Collection Phase

Use this section to record discoveries while collecting screenshots.

  • Capture the same approximate viewport size where practical; otherwise record the viewport dimensions.
  • Prefer screenshots containing enough surrounding UI to understand context, but crop away unrelated content when the component itself becomes difficult to inspect.
  • Capture both the resting state and meaningful interaction states where possible.
  • Record actual measured dimensions separately from visual impressions. A screenshot that "looks compact" is not itself evidence of a particular pixel height.
  • Pay particular attention to the relationship between: header height, row height, cell padding, typography, gridline weight and selection treatment.
  • For Notion and Airtable, record measurements from a consistent zoom/browser environment where possible so comparisons are meaningful.
  • Do not assume that a reference's implementation should be reproduced. Record the specific design principle or solution that appears relevant to this application.
  • Keep behavioral requirements separate from visual observations. Existing Dojo behavior should only be changed when the redesign explicitly calls for a behavioral change.

A couple of deliberate choices in this Grid version: the reference gallery is the first substantive section, because that matches the phase you are entering now; the measurement matrix is separate so you can later turn observations such as row height, header height, cell padding and gridline weight into actual design-system decisions; and I have kept the proposed Grid deliberately conservative rather than trying to “design” the final Grid before the comparative evidence is collected.

I also left the proposed numeric Grid values explicitly marked PROVISIONAL. That is consistent with the current Button and TextBox Labs, where the component-specific measurements are being used as hypotheses rather than prematurely promoted to the global Design System. The existing project direction around restrained color, semantic tokens, density and no general elevation is likewise carried through from the current documents. r1
