UI Redesign — Design System

Living specification for the application's visual language, interaction states, design tokens and component rules.
Purpose of this document
This is the working design authority. Decisions established during UI redesign sessions should be incorporated here so that future conversations do not need to reconstruct design intent from conversation history.

1. Design-System Principles

  1. System before component. Establish shared rules before creating component-specific exceptions.
  2. Semantic rather than arbitrary. Tokens describe their role, not merely their raw visual value.
  3. Restrained visual language. Avoid unnecessary visual noise.
  4. Interaction should be visible but quiet. State changes should be discoverable without overwhelming the content.
  5. Desktop productivity first. Information density and efficient interaction matter.
  6. Accessibility is part of the component specification. It is not an afterthought to visual styling.
  7. Behavior and visual treatment remain separate. Dojo behavior should not be changed merely to achieve a visual effect.

2. Visual Treatment Model

The system deliberately does not use "elevation" as a universal hierarchy mechanism.

Established rule — Elevation

There is no general elevation tier such as elevation-1, elevation-2, elevation-3, etc. Surfaces should communicate hierarchy through composition, borders, contrast, spacing and context rather than assuming that everything needs a shadow.

A specific component may eventually require a shadow for a particular reason, such as a floating overlay. If so, that is a component-level treatment, not a general design role.

4. Interaction States

The standard state vocabulary is:

State Meaning General visual principle
Normal Resting interactive state. Quiet/default appearance.
Hover Pointer is over an interactive target. Subtle affordance; light Claro Blue is preferred where appropriate.
Focus-visible Keyboard/accessibility focus is active. Clear, standardized focus treatment.
Pressed / Active Control is being activated or held. Stronger than hover; should communicate physical activation.
Disabled Control is unavailable. Reduced visual emphasis without becoming ambiguous.
Selected Persistent application selection/toggle state. Must remain distinguishable from transient hover.
Selected + Hover Selected item under pointer. Selected state remains dominant; hover may subtly modify it.
Selected + Focus Selected item has keyboard focus. Selection and focus must remain independently understandable.
Error Invalid/problem state. Semantic error treatment.
Warning Potential problem requiring attention. Semantic warning treatment.
Read-only Content is viewable but not editable. Must communicate non-editability without appearing disabled.

5. Hover Treatment

Current design direction

Transparent regular/dialog buttons should preferably reveal a very-light Claro Blue surface on hover rather than a neutral gray surface.

This provides a small amount of color only during interaction and fits the overall restrained/near-monochrome visual direction.

The hover token must remain semantic. Components should reference --ui-color-surface-hover rather than embedding a specific Claro Blue value.

This treatment is not automatically prescribed for ActionBars, toolbars, menus, grids or other specialized components. Their behavior will be determined during their own component specifications.

6. Typography

Typography is a shared foundation and should eventually be expressed through semantic tokens.

Candidate token families:

  • --ui-font-family
  • --ui-font-size-xs
  • --ui-font-size-sm
  • --ui-font-size-md
  • --ui-font-size-lg
  • --ui-font-weight-normal
  • --ui-font-weight-medium
  • --ui-font-weight-semibold

Exact values remain TBD pending broader component comparison.

7. Spacing and Density

Spacing should use a controlled scale rather than arbitrary component-specific padding.

The application should eventually support density profiles. Candidate profiles are Compact, Default and Comfortable. Exact control heights, spacing values and profile behavior remain to be established.

8. Borders and Radius

Borders should generally be quiet and functional rather than decorative. Border radius should likewise be systematic rather than independently chosen by every component.

The exact radius scale remains TBD.

9. Focus Treatment

Focus is a first-class interaction state. It must not be confused with hover or selection.

The eventual focus treatment should:

  • Be visually clear.
  • Be consistent across component families where practical.
  • Work against both light and darker surfaces where required.
  • Respect keyboard accessibility.
  • Avoid being mistaken for a persistent selection state.

10. Button System

Button is the first component being developed as a formal component specification. The Button Design Lab is the working visual artifact.

The Button specification will ultimately define:

  • Button roles/variants.
  • Normal state.
  • Hover state.
  • Focus-visible state.
  • Pressed/active state.
  • Disabled state.
  • Selected/toggled state where applicable.
  • Icon-only buttons.
  • Text + icon buttons.
  • ActionBar versus regular/dialog buttons.
  • Sizing and density.
  • Icon alignment and spacing.
  • Keyboard/accessibility behavior.

11. Component Specification Template

Each component should eventually have a specification containing at least:

  1. Purpose and role.
  2. Variants.
  3. Dimensions/density.
  4. Typography.
  5. Normal state.
  6. Hover state.
  7. Focus-visible state.
  8. Pressed/active state.
  9. Disabled state.
  10. Selection states if applicable.
  11. Validation/error states if applicable.
  12. Iconography if applicable.
  13. Keyboard behavior.
  14. Accessibility requirements.
  15. Exceptions to global rules.
  16. Relevant design tokens.

14. Maintenance Rule

This document should contain conclusions, not the entire history of the conversation that produced them. If a decision changes, update the decision rather than accumulating contradictory historical rules.

Temporary experiments belong in the relevant Design Lab. Once an experiment is accepted as a design rule, promote the result into this document.
