UI Design Lab — RadioButton

Working visual specification, interaction-state laboratory and comparative-reference gallery for the RadioButton component.

Current design hypothesis: RadioButtons should remain visually restrained and information-dense. The selected indicator should be immediately recognizable without requiring a persistent colored container. Hover should provide a quiet interaction cue, while focus-visible should remain clearly distinguishable from both hover and selection.

Reference-image methodology: The comparative screenshots in this Lab are intended to document actual visual treatments observed in Notion, Airtable, Windows/system UI, Material and the current/proposed application. They are evidence for comparison and design evaluation, not specifications to copy. Where possible, record actual measurements separately rather than estimating dimensions from the screenshots.

4.2 Recommended Screenshot Subjects

  • Individual unselected RadioButton — enough surrounding context to identify the label and normal spacing.
  • Individual selected RadioButton — capture the selected indicator at a useful scale.
  • Radio group — capture vertical or horizontal spacing, label alignment and relationship between options.
  • Hover state — capture only where the reference system provides a meaningful hover treatment.
  • Focus state — capture keyboard focus where practical.
  • Disabled state — capture both disabled/unselected and disabled/selected where the reference system distinguishes them.
  • Long-label example — useful for determining wrapping and vertical alignment.
  • RadioButton beside other controls — useful for determining whether its size, label baseline and spacing harmonize with TextBox, Checkbox and Button.

6. RadioButton Design Questions

Items that should be settled before RadioButton becomes a finalized component specification.

  1. What should the default RadioButton diameter be?
  2. Should the RadioButton use a visible border in its normal unselected state?
  3. How strong should the selected indicator be?
  4. Should the selected state use the global accent color, a component-specific token, or another treatment?
  5. Should the selected outer ring and inner dot use the same color?
  6. Should hover modify the RadioButton itself, the surrounding label target, or both?
  7. Should the very-light Claro Blue hover surface apply to the complete clickable option?
  8. Should a selected RadioButton receive a different hover treatment from an unselected RadioButton?
  9. How should focus-visible be represented without confusing it with selection?
  10. Should the focus ring surround only the RadioButton or the complete label/click target?
  11. What is the appropriate control-to-label spacing?
  12. What is the appropriate spacing between options in a vertical group?
  13. What is the appropriate spacing between options in a horizontal group?
  14. What should the minimum clickable target size be?
  15. How should long labels wrap?
  16. How should multi-line labels align relative to the RadioButton?
  17. What is the visual distinction between Disabled and Disabled + Selected?
  18. How should Error and Warning states be communicated without relying on color alone?
  19. Should a RadioButton have an explicit Read-only state, or is the group simply unavailable for interaction?
  20. Which dimensions should become shared control primitives with Checkbox and other selection controls?
  21. Which RadioButton decisions should become global semantic tokens?

8. Accessibility and Keyboard Questions

  • What receives DOM focus?
  • Is the focus indicator clearly distinguishable from the selected indicator?
  • Does Tab enter and leave the RadioButton group predictably?
  • Are Arrow keys used to move between radio options?
  • Does Space select the focused option?
  • What happens when a group has no initial selection?
  • Does Enter have any special behavior, or is selection performed through Space/Arrow-key interaction?
  • Are disabled options skipped appropriately?
  • Is the group exposed correctly to assistive technology?
  • Is the group label programmatically associated with the RadioButton group?
  • Are validation states communicated through text/semantics as well as visual styling?

10. Current Decisions / Working Hypotheses

These are working decisions and hypotheses. Promote them into Design\_System.html only when sufficiently established across the component system.

  • D-001: The RadioButton should remain visually restrained in its normal state.
  • D-002: Persistent color should not be used merely to establish interactivity.
  • D-003: The selected state must be immediately distinguishable from the unselected state.
  • D-004: Hover should provide perceptible but restrained interaction feedback where the surrounding reference/component family supports it.
  • D-005: Focus-visible must be unmistakably different from both hover and selection.
  • D-006: Disabled states should reduce visual emphasis without making the selected/unselected distinction ambiguous.
  • D-007: Validation states must not rely on color alone.
  • D-008: RadioButton geometry should eventually be evaluated alongside Checkbox and other selection controls so that shared primitives can be identified.
  • D-009: Semantic tokens should be used even while initial values remain provisional.

11. Notes for Future Iterations

Primary comparison to make: Do the Notion, Airtable, Material and Windows references suggest a common visual/interaction primitive that should be shared with Checkbox, or do RadioButton and Checkbox require deliberately different treatments?

Primary geometry comparison: Compare outer diameter, border thickness, selected-dot ratio, control-to-label spacing and minimum target size.

Primary state comparison: Compare Normal, Selected, Hover, Focus-visible and Disabled before settling the component's final token values.

Once the RadioButton design is sufficiently settled, the final decisions should be promoted to Design\_System.html. Provisional values in this Lab should then be replaced by the approved semantic tokens where appropriate.

The same comparative-reference methodology should subsequently be used for Select/combo control, Checkbox, Menu, Dialog, Grid and the remaining representative components.

A couple of deliberate choices in this version are worth flagging. First, I’ve treated RadioButton as a selection-control family member, rather than simply copying the Button or TextBox Lab structure. Second, the measurement table is intentionally included because your plan to obtain exact Notion measurements is particularly useful here: outer diameter, dot-to-ring ratio, label gap, option spacing and target size are precisely the kinds of values that can reveal whether RadioButton and Checkbox should eventually share geometry tokens.

I also kept the proposed values provisional, consistent with the current TextBox Lab and Design System: the existing documents explicitly say that component-level values should not automatically become global tokens until they have been validated across the system. r1

When you repeat the process for the next component, we can use this same structure while adapting the reference categories and state vocabulary to that particular control.
