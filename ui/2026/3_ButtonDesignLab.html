4. Primary Treatment, Default Actions & Focus

Token names and semantic roles are currently more authoritative than the provisional numeric/color values. The values remain subject to validation as the Button and broader component system mature.

Primary styling, default-action status and keyboard focus are separate concepts. They serve different purposes and MUST NOT be treated as interchangeable.

Primary Treatment Is Deliberate Primary styling provides persistent visual emphasis for an action that merits it in the current interface context. It is not the automatic appearance of a button simply because that button is the default action, appears first, or is the most likely action to be taken.

Use Primary treatment selectively, when it materially improves discoverability, clarifies the intended next step, or establishes a useful visual hierarchy.

Examples:

  • A prominent New button in an unfamiliar or complex application may benefit from Primary treatment because it helps users discover how to begin creating something.
  • A Save button in an ordinary editing dialog does not automatically require Primary treatment merely because saving is the expected outcome.
  • An OK button in a conventional confirmation or settings dialog does not automatically require Primary treatment merely because it is the default action.
The objective is meaningful emphasis, not maximum emphasis. If every button is Primary, Primary loses much of its ability to distinguish important actions.

Default Action Is a Behavioral Role A default action is the action associated with the Dialog's default/accept behavior, including Enter-key activation where appropriate.

Default-action status MUST be represented independently of the button's visual variant. A Regular/Secondary button may be the default action without becoming Primary.

Focus Is an Interaction State Focus indicates which control currently receives keyboard interaction. The existing Button focus treatment should make this state clearly perceptible and distinguishable from hover, pressed and selected states.

When a Dialog opens, its appropriate default action may also receive initial keyboard focus, where this is suitable for the Dialog's purpose and interaction context. This does not require the button to use Primary styling.

Focus and default-action status are related but distinct: focus determines the current keyboard interaction target, while default-action status determines the Dialog's designated default behavior. They may coincide, but MUST NOT be assumed to be identical in every situation.

Governing Rule Choose the button's visual variant according to the emphasis warranted by its role and context. Determine default-action behavior and focus independently.

A button MUST NOT receive Primary styling solely because it is the default action. Conversely, a genuinely important action MAY receive Primary styling whether or not it is the default action.

This rule applies consistently across page-level controls, ActionBar buttons and Dialog actions.

Observation: Regular buttons should remain visually quiet in their normal state. The principal color change occurs on hover, rather than being permanently present. Primary styling is reserved for actions that warrant persistent emphasis based on their context and purpose. Focus is an independent interaction state and must remain distinguishable from hover, pressed and selected states.

7. Design Questions to Resolve

Items that should be settled before Button becomes a finalized component specification.

The principal Button visual/interaction-direction questions have now been resolved and have been checked against representative reference UIs. Remaining questions concern final taxonomy, specialized behavior and numeric/token values.

  1. What is the final distinction between Primary, Secondary and Transparent/Tertiary actions?
    The currently proposed design (Section 1) is acceptable.
  2. How should ActionBar buttons differ from regular/dialog buttons?
    No Difference
  3. How should hover interact with a selected/toggled button?
    As currently proposed (Section 2), selected treatment + light blue hover treatment.

    Yes.

7. Current Decisions

Promote these into Design_System.html when they are sufficiently established.

  • D-001: The overall UI should remain restrained and predominantly neutral.
  • D-002: Persistent color should not be used merely to make a regular button recognizable when a quieter treatment is sufficient.
  • D-003: Regular/secondary buttons should use the restrained secondary-style treatment with darkBlue text rather than a permanent blue fill.
  • D-004: Very-light Claro Blue is the preferred and sufficiently perceptible hover treatment for appropriate transparent buttons.
  • D-005: Pressed should use the existing subtle darkening treatment.
  • D-006: Focus should retain the existing Button Lab focus treatment and remain distinguishable from hover without unnecessary visual noise.
  • D-007: Elevation/shadow is not a general Button visual-treatment mechanism.
  • D-008: Semantic tokens should be used even when their initial values remain provisional.
  • D-009: Primary treatment is an intentional emphasis choice, not the automatic styling of a default action.
  • D-010: Default-action semantics and keyboard-focus state are independent of the Button's visual variant.
  • D-011: A Regular/Secondary button may be the default action and receive focus without Primary styling.
  • D-012: Primary treatment should be used selectively when it materially improves action discoverability or communicates meaningful visual hierarchy.

9. Notes for Future Iterations

This Lab is intentionally not a final implementation. It is the place where visual hypotheses can be tested before they become design-system rules.

Once the Button design is sufficiently settled, the final decisions should be promoted to Design_System.html and the provisional values in this Lab should be replaced with the approved semantic tokens.

The same pattern should subsequently be used for TextBox, Select, Checkbox, Menu, Dialog, Grid and other representative components.
