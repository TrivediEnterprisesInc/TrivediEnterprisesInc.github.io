UI Redesign — Context & Requirements

Canonical project context for the application's Web/Desktop UI redesign.
Document role: Stable project context and requirements.
Status: Living document — update when a fundamental requirement or project assumption changes.
Last established: August 2026

1. Project Overview

The project is an application builder, broadly comparable in concept to modern application-building platforms, but substantially heavier and more desktop/productivity-oriented.

The application has two clients: Desktop and Web. The Web client currently uses the Dojo UI framework.

The objective of this effort is to finalize a modern, coherent, highly usable visual UI for the Web client while preserving the application's existing behavioral architecture.

2. Redesign Objective

The redesign is not intended to make individual widgets look attractive in isolation. It is intended to establish a coherent application-wide design system that can subsequently be applied consistently to the complete widget inventory.

The design system should provide:

  • A restrained, modern visual language.
  • High information density appropriate for a serious application builder.
  • Strong consistency between components.
  • Clear and predictable interaction states.
  • Good keyboard and accessibility behavior.
  • A semantic token architecture suitable for future user customization.
  • A clear separation between visual styling and component behavior.
  • A visual reference/testing environment that can be maintained as the design evolves.

3. Redesign Philosophy

3.1 Design-system first

The redesign should be treated as a design-system exercise rather than merely a widget-by-widget CSS exercise.

Common design primitives should be identified before large-scale component styling begins. Components should consume shared semantic design tokens rather than independently inventing values for color, focus, spacing, borders, etc.

3.2 Inspiration rather than copying

The primary reference systems are:

  • Notion — restrained visual language and low visual noise.
  • Airtable — productivity-oriented controls and information density.
  • Windows/system UI — desktop conventions, keyboard interaction and familiar application behavior.
  • Material Design — explicit component/state definitions and systematic design vocabulary.

These systems are references for principles and solutions, not templates to be copied wholesale.

4. Visual Direction

The desired overall appearance is restrained, predominantly neutral, and content-oriented. Persistent color should be used sparingly rather than making the application visually saturated.

Color should increasingly function as an interaction and semantic signal rather than merely as persistent decoration.

Established direction: No general elevation role.

Elevation is not a general-purpose Visual Treatment role in this design system. The system should not adopt a Material-style assumption that controls or surfaces generally need shadows/elevation to communicate hierarchy.

5. Interaction-State Vocabulary

The original Normal / Focused / Clicked / Disabled model is expanded into a standard vocabulary. Individual components will use only the states that are meaningful for them.

  • Normal
  • Hover
  • Focus-visible
  • Pressed / Active
  • Disabled
  • Selected
  • Selected + Hover
  • Selected + Focus
  • Error
  • Warning
  • Read-only

6. Hover-State Direction

Current design direction: Very-light Claro Blue hover surface.

For regular/dialog controls that are visually transparent in their resting state, the preferred hover treatment is a subtle, very-light Claro Blue surface rather than the more conventional neutral-gray surface.

The intention is to introduce a small amount of color only when interaction occurs, while retaining the application's predominantly neutral appearance.

This is a design direction rather than a finalized numeric color value. The exact token value will be established during the Button Design Lab and subsequent component validation.

The hover treatment should not automatically be applied identically to every component family. ActionBars, toolbars, grids, menus, selections and other specialized controls may require their own interaction treatment.

7. Density

The application is a heavy productivity/application-building environment. Information density is therefore an explicit design concern.

The design system should eventually support a controlled density model rather than having each component independently determine its dimensions.

Candidate density levels discussed conceptually include Compact, Default and Comfortable. Exact dimensions remain to be established.

8. Semantic Design Tokens

Tokens should describe semantic roles rather than expose arbitrary raw color values to components.

Examples include:

  • --ui-color-accent
  • --ui-color-surface
  • --ui-color-surface-hover
  • --ui-color-surface-active
  • --ui-color-border
  • --ui-color-border-focus
  • --ui-color-focus-ring
  • --ui-color-text
  • --ui-color-text-muted
  • --ui-color-text-disabled

Exact values will be developed progressively through the component labs.

9. Separation of Concerns

Layer Responsibility
Structure DOM/layout and component structure.
Behavior Dojo/JavaScript behavior and interaction logic.
Visual Design CSS and semantic design tokens.
Accessibility ARIA, keyboard behavior, focus management and accessible states.

AI-generated CSS should be constrained primarily to the visual-design layer and should not inadvertently redesign component behavior.

10. Accessibility and Keyboard Requirements

Component specifications must address behavior as well as appearance. Depending on the component, specifications should include:

  • What receives focus?
  • When is the focus indicator visible?
  • Enter behavior.
  • Space behavior.
  • Escape behavior.
  • Tab order.
  • Arrow-key behavior where applicable.
  • Disabled behavior.
  • Selected-state behavior.

11. Component-by-Component Process

  1. Inventory components.
  2. Classify components into families.
  3. Identify shared design primitives.
  4. Study relevant reference UIs.
  5. Create a component/state specification.
  6. Define or refine semantic tokens.
  7. Create/update the visual Design Lab.
  8. Generate CSS only after the design direction is sufficiently established.
  9. Test the result across representative components.
  10. Use the Labs as an ongoing visual regression/reference suite.

12. Representative Components

The initial representative set should include components that expose most of the fundamental design decisions:

  • Button
  • TextBox / text input
  • Select / combo control
  • Checkbox
  • Menu
  • Dialog
  • Grid

Button is currently being used as the first detailed component specification and Design Lab.

13. Golden Reference / Design Lab Concept

The project should maintain visual reference pages that allow the design to be evaluated interactively rather than relying solely on screenshots.

A typical component Lab should eventually include:

  • Reference implementations/inspiration from Notion, Airtable, Windows and Material where useful.
  • Current Dojo implementation.
  • Proposed target implementation.
  • Interaction states.
  • Relevant variants and sizes.
  • Annotations explaining significant design decisions.
