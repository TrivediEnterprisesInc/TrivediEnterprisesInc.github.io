B. I would modify your workflow slightly

Your proposed workflow is:

  1. Study competitors.
  2. Choose a uniform approach.
  3. Generate CSS.

I would turn it into something closer to:

  1. Inventory the components.
  2. Identify the underlying design primitives.
  3. Study the competitors.
  4. Create a component/state specification.
  5. Define your design tokens.
  6. Create visual reference boards.
  7. Generate the CSS.
  8. Test the resulting system across components.

The crucial addition is design tokens/primitives before component CSS.

1. Don't start with Button

I'd actually start by extracting the things that buttons, inputs, menus, grids, dialogs, etc. have in common.

For example:

  • background colors
  • foreground/text colors
  • border colors
  • hover colors
  • focus treatment
  • active/pressed treatment
  • disabled treatment
  • border radius
  • border width
  • shadows
  • font family
  • font sizes
  • font weights
  • control heights
  • horizontal/vertical padding
  • spacing scale
  • icon sizes
  • animation/transition timing

Those become your design vocabulary.

Then a Button isn't independently deciding what "focused blue" means. It consumes the global focus token. A TextBox consumes the same focus token. A TreeView consumes it. A Grid consumes it.

That is what will make the eventual user customization capability much more powerful.

2. Think in terms of semantic tokens, not just colors

For example, rather than having:

--blue-500: #3b82f6;

I'd prefer something conceptually like:

--ui-color-accent: ...;


--ui-color-focus-ring: ...;
--ui-color-surface: ...;
--ui-color-surface-hover: ...;
--ui-color-surface-active: ...;
--ui-color-border: ...;
--ui-color-border-focus: ...;
--ui-color-text: ...;
--ui-color-text-muted: ...;
--ui-color-text-disabled: ...;

The distinction is important. Users should ultimately be able to say "make my application use a purple accent" rather than having your system expose 47 unrelated blue values.

3. Add state matrices

Your Normal / Focused / Clicked / Disabled idea is good, but I'd expand the state model slightly.

For interactive components, I'd consider at least:

  • Normal
  • Hover
  • Focus-visible
  • Pressed / Active
  • Disabled
  • Selected
  • Selected + Hover
  • Selected + Focus
  • Error
  • Warning
  • Read-only

Not every widget needs every state. The point is to establish a standard state vocabulary so that each component doesn't invent its own interpretation.

4. Separate visual decisions from behavioral decisions

This is particularly important with Dojo.

I'd establish explicitly:

  • Structure: DOM/layout
  • Behavior: Dojo/JavaScript
  • Visual design: CSS/design tokens
  • Accessibility: ARIA/keyboard/focus behavior

Then your AI-generated CSS should ideally be constrained to the visual layer rather than allowing it to inadvertently redesign component behavior.

I'd also distinguish "inspiration" from "copying"

The four sources you selected are actually a very interesting combination because they represent substantially different design philosophies:

  • Notion — extremely restrained, content-oriented, low visual noise.
  • Airtable — application/productivity UI with stronger affordances and denser controls.
  • Windows — desktop-oriented interaction, system conventions, accessibility and keyboard interaction.
  • Material — a formalized design system with unusually explicit component/state rules.

Rather than asking "Which one should my Button look like?", I'd ask "What design principle does each system solve well?"

For example, you might end up with:

Area Possible influence
Overall visual restraintNotion
Dense productivity controlsAirtable
Desktop conventionsWindows
Systematic state definitionsMaterial

That should result in something that is inspired by the best characteristics of several systems rather than looking like a clone of any one of them.

One thing I'd add that you didn't mention: density

For an app builder, this can be surprisingly important.

You may eventually want a global density setting:

Compact
28px controls
4px spacing


Default
32px controls
6px spacing

Comfortable
38px controls
8px spacing

Because you're building a fairly heavy application rather than a simple marketing UI, information density is likely to matter more than it does in something like a typical Material-based application.

And don't overlook keyboard/focus behavior

This is one area where screenshots alone can mislead you.

For a desktop/Web app builder, I'd make keyboard behavior part of the component specification alongside the screenshots:

  • What receives focus?
  • Is the focus ring visible only for keyboard navigation?
  • What does Enter do?
  • What does Space do?
  • What does Escape do?
  • How does Tab move through the component?
  • What happens with arrow keys?
  • What happens when disabled?
  • What happens when selected?

That will be particularly important for grids, trees, menus, dialogs, tabs, combo boxes and other complex widgets.

My recommended overall process

  1. You give me your widget inventory.
  2. We classify them into component families.
  3. We establish the foundational design tokens.
  4. We pick a small representative set of components — e.g. Button, TextBox, Select, Checkbox, Menu, Dialog, Grid.
  5. For each, we create the AirTable / Notion / Windows / Material / Current Dojo / Proposed comparison.
  6. We use those to establish the visual language.
  7. We turn the visual language into a formal component/state specification.
  8. Only then do we generate the CSS.
  9. We use the UI Lab as a regression suite while working through the remaining widgets.

I would not start by generating CSS for all your widgets. I'd first get perhaps 5–8 representative widgets looking exactly right. Once those establish your design language, the remaining components become much easier and the AI-generated CSS is considerably less likely to drift.
