UI Design Lab — Dialog

Working visual specification, comparative reference laboratory and state laboratory for the Dialog component.

Current design hypothesis: A Dialog should establish a clear temporary interaction context without introducing a generic application-wide "elevation" hierarchy. Its hierarchy should primarily come from the overlay, surface contrast, boundary, composition and spacing. Any shadow used by the Dialog is a component-level floating-surface treatment rather than a global elevation token.
Important: The numerical values in this document are provisional starting points only. The purpose of this Lab is to collect comparative evidence before finalizing Dialog geometry, overlay treatment, typography, spacing, radius and action layout.

1. Purpose and Role

The Dialog provides a temporary interaction context that interrupts or temporarily supersedes the underlying application surface.

The final specification should distinguish between dialogs used for:

  • Confirmation / decision making
  • Short-form data entry
  • Multi-field editing
  • Information / acknowledgement
  • Warnings and potentially destructive actions
  • Longer workflows that may require a larger dialog
  • Dialogs containing scrollable content

The Dialog should not automatically be treated as a generic container for arbitrary application content. Its visual and interaction treatment should communicate that it is a temporary modal context.

4. Live Interaction Test

Use this section to evaluate the Dialog in actual browser interaction rather than only as a static visual.

Edit record

Use Tab to move through the controls. Evaluate focus visibility, tab order, action ordering and whether the Dialog remains visually distinct from the underlying page.

Keyboard test: Tab through every focusable element. Test Enter, Escape, Shift+Tab and the behavior when the Dialog is opened and closed. Determine whether focus returns correctly to the invoking control.

8. Header, Content and Footer Structure

Evaluate whether the Dialog should use three visually distinct structural regions or whether some Dialog types should omit one or more regions.

Region Questions to evaluate Current hypothesis Decision
Header Should the title have its own bounded region? Is a separator required? Should a close button appear here? Distinct title/header is appropriate for most dialogs.
Content What is the standard horizontal/vertical padding? Does content scroll independently? Content should remain information-dense and use shared control spacing.
Footer Should actions have a separate surface? Should the footer have a border? How are actions aligned? Right-aligned actions are a candidate for desktop productivity UI.
Close control Is a close icon always present? Where is it located? Is it redundant with Cancel/Close? TBD through comparative review.

9. Dialog Action Area

The Dialog action area should be evaluated together with the Button Lab. Dialog-specific work should establish layout and hierarchy, while Button visual treatment should remain governed by the Button component specification.

  • Primary versus secondary action hierarchy
  • Action ordering
  • Horizontal versus vertical action layout
  • Spacing between actions
  • Distance between actions and Dialog edge
  • Default action indication
  • Disabled action treatment
  • Destructive action treatment
  • Cancel / dismiss behavior
Important separation: Do not independently redesign the Button inside this Lab merely because it appears inside a Dialog. The Dialog Lab should determine placement, spacing and contextual hierarchy; the Button Lab remains the authority for Button visual treatment.

11. Dialog Behavior Questions

  1. Does clicking outside the Dialog dismiss it?
  2. Does pressing Escape dismiss it?
  3. Are there Dialog types for which Escape must not dismiss the Dialog?
  4. Does focus move automatically into the Dialog when it opens?
  5. Where does focus go when the Dialog closes?
  6. Is focus trapped within the modal Dialog?
  7. Can the underlying page receive pointer interaction while the Dialog is open?
  8. Does the underlying page scroll while the Dialog is open?
  9. What happens when Dialog content exceeds the viewport height?
  10. Does the Dialog remain centered, or can it use another positioning strategy?
  11. How are nested dialogs handled, if at all?
  12. How does the Dialog behave when the viewport is resized?

12. Accessibility and Keyboard Questions

  • Does the Dialog expose the correct accessible role?
  • Is the Dialog title programmatically associated with the Dialog?
  • Is descriptive content associated where appropriate?
  • Does keyboard focus move into the Dialog predictably?
  • Is focus trapped correctly while the Dialog is modal?
  • Does Tab order remain predictable?
  • Does Shift+Tab behave correctly?
  • Does Escape perform the expected dismiss/cancel behavior?
  • Does Enter activate the intended default action without causing accidental submission?
  • Are destructive and validation states communicated through more than color?
  • Can the Dialog be operated completely without a pointer?

14. Dialog Design Questions

  1. How strong should the Dialog boundary be against the underlying page?
  2. Should the Dialog have a visible border, shadow, or both?
  3. How much visual weight should the overlay contribute?
  4. Should the Dialog surface remain pure white or use a subtle alternate surface?
  5. What Dialog corner radius fits the shared component system?
  6. Should header and footer surfaces be visually differentiated from content?
  7. Should header/footer separators be visible?
  8. What are the appropriate Dialog widths for Compact, Default and Comfortable density profiles?
  9. What is the minimum useful Dialog width?
  10. What is the maximum useful Dialog width before the component should become a different layout pattern?
  11. How should the Dialog relate visually to the existing Button and TextBox components?
  12. Should the Dialog overlay use the same semantic color architecture as the rest of the application?
  13. Does the Dialog require a close icon in addition to explicit actions?
  14. What action alignment is most appropriate for this desktop productivity UI?
  15. Which Dialog properties should become shared semantic tokens?

17. Open Questions / Evidence to Collect

Before finalizing the Dialog:
  • Collect at least one representative Notion Dialog screenshot.
  • Collect at least one representative Airtable Dialog screenshot.
  • Collect at least one Windows/system Dialog screenshot.
  • Collect at least one Material Dialog screenshot.
  • Capture the current application's Dojo Dialog.
  • Record approximate width, height, padding, radius and action spacing for each.
  • Record overlay color/opacity where measurable.
  • Record whether header/footer regions are separated by borders.
  • Record whether actions are right-aligned, left-aligned or otherwise arranged.
  • Record how Escape, outside-click and focus are handled.
  • Identify which patterns recur across several references rather than relying on one reference implementation.

This Design Lab is intended to remain a working visual artifact. Once the Dialog direction is sufficiently established, the conclusions should be promoted into the global Design System and the final Dialog component specification, while experimental material can remain here as supporting evidence.

This one is intentionally a little more measurement-oriented than the TextBox Lab, because Dialogs have several additional dimensions worth capturing: overlay opacity, dialog width/height, header/footer geometry, action placement, and the relationship between the floating surface and the underlying application.

When you move on to the next component, we can keep this same Lab architecture and only change the component-specific anatomy, states, reference matrix, and measurement fields.
